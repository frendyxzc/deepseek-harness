本模块是纯数据驱动的回归测试集，按被测入口划分为 acp/、sdk/、session/、web/ 四个子目录，每个子目录对应一种 `dsh --profile` 入口：
- `acp/acp.snapshot.ts` 使用 `defineAcpSnapshotSuite` 枚举 scenario 并读取各自 `snapshot.yml` 清单驱动；
- `sdk/sdk.snapshot.ts` 通过 `@deepseek-ai/dsh-sdk-client` 启动真实 `dsh --profile sdk` 子进程，以 JSON-RPC 驱动一轮或多轮对话，收集通知流、`RunResult` 与 `.dsh/sessions` 下的持久化日志；
- `session/headless.snapshot.ts` 借助 `@deepseek-ai/dsh-loader-smoke` 直接 spawn `dsh --profile headless`，从 `.dsh/sessions` 拉取持久化日志并与 fixture 比对；
- `web/` 下每个场景仅含 `snapshot.yml` 与期望 UI/markdown/json 产物，由上层 web 测试框架加载。

所有场景共享同一套固定点机制：每个 scenario 目录必须包含 `snapshot.yml`（声明 `profile`、`composition`、`recording`、`header.class`、可选 `replay.override`、`environment`、`permission`、`platform`），以及一个或多个 `session[.N].jsonl` 作为输入；可选的 `system-prompt.expected.md`、`tool-schemas.expected.json`、`notifications.expected.jsonl`、`result.expected.json`、`stdout.expected.jsonl`、`workspace.expected/` 作为黄金文件。`cordis.yml` / `model.cordis.yml` / `cordis.snapshot.yml` 用于按 composition 组织配置补丁，并通过 `materializeProfilePatch` 在运行时展开为 `.snapshot-patches/*`。头部（request header）采用 pin/changes 机制：每个 composition/header class 只能有一个 pin 场景，其他场景复用其 header 与 prompt/schema 侧车，变更通过 `header.changes` 描述增量。运行模式由 `DSH_SNAPSHOT` 环境变量控制：`replay`（默认）、`record`、`refresh`，分别对应只读比对、重新录制、基于旧 fixture 稳定化后重写。所有可变标识（sessionId、messageId、cwd 等）经 `normalizeSessionSnapshots`、`redactSessionSnapshotIds`、`tokenizeSessionFixtureCwd` 等工具函数归一化后再比对，保证跨平台可重复。
