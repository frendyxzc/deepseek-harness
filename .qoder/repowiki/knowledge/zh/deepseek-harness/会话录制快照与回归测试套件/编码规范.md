- 每个 scenario 目录必须包含 `snapshot.yml` 清单，声明 `profile`、`composition`、`recording`、`header.class` 等元数据，并由对应入口脚本解析驱动。
- 会话输入统一存放在 `session.jsonl`（及 `session.N.jsonl` 表示子会话），禁止在 `input.json` 中重复定义任务，任务来源必须是 session 中的 user/message。
- 对 request header 的断言通过 pin/changes 机制集中管理：每个 composition/header class 仅允许一个 pin 场景，其余场景引用其 `system-prompt.expected.md` 与 `tool-schemas.expected.json` 侧车。
- 工作区产物若发生写入，需将完整最终状态提交到 `workspace.expected/` 并在 manifest 中标记 `workspace.final: true`；空结果用 `.empty` 占位文件表示。
- 所有 fixture 在写入前必须经过 `scrubSessionSnapshot`、`tokenizeSessionFixtureCwd`、`redactSessionSnapshotIds`、`stabilizeFixtureMessageIds` 等归一化流程，确保提交物不含易变标识。
- 场景通过 `cordis.yml` / `model.cordis.yml` / `cordis.snapshot.yml` 以 composition 为单位组织配置补丁，运行时由 `materializeProfilePatch` 展开到 `.snapshot-patches/`，避免硬编码绝对路径。
